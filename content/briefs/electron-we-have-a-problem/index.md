# Electron, we have a problem

Many Electron apps auto-update without verifying signatures. Many also still trust the compromised eMudhra certificates. Together, that lets an attacker on your network install malware on your machine.

If you're a user, uninstall affected apps and install patched versions manually. If you're a vendor, please verify signatures on your auto-updates.

<socials/>

## Cypher-SaaS

My hobby this year was breaking the crypto in privacy products like [Proton](https://schaerli.org/weblog/5-proton/), [Internxt](https://schaerli.org/weblog/6-internxt/) and [Filen](https://schaerli.org/weblog/7-filen/). My biggest gripe with these [Cypher-SaaS](https://schaerli.org/weblog/7-filen/#zeroknowledgeencryption) products is that they rarely admit browser crypto doesn't make sense. They [claim](https://web.archive.org/web/20260522105556/https://proton.me/) that nobody, not even the vendor, can access your data. Yet the vendor could serve a malicious script to a few users and backdoor the encryption. It would be trivial and hard to detect.

The usual [advice](https://web.archive.org/web/20260526121017/https://proton.me/blog/cryptographic-architecture-response) is to use desktop app instead, where code can be signed and crypto isn't re-fetched on every page load. Because most Cypher-SaaS started off as websites, a common choice is to build desktop clients with [Electron](https://www.electronjs.org/). This essentially just bundles the website into a local app running inside a customized browser. However, Electron's update ecosystem is [messy](https://blog.doyensec.com/2026/02/16/electron-safe-updater.html) and the mainstream libraries only have partial or no signature support, which leads some vendors to skip it and rely on TLS alone to protect the update channel.

## eMudhra Intermediate CA Compromise

Then in October 2026, [emudhra.we-have-a-problem.com](https://emudhra.we-have-a-problem.com/) showed that a couple eMudhra intermediate CAs, trusted to sign certificates for any website, used tiny private keys that are trivial to recover.

Browsers fixed it quickly, shipping revocation lists within hours, it didn't even require a browser update. But Electron [does not have](https://github.com/electron/electron/pull/7252) Chromium's component updater, which is what delivers those lists, so there was no easy remediation. Electron fixed it by [hardcoding](https://github.com/electron/electron/blob/817c43f925677eb88034bfba4f0b8dfd28e7ad20/patches/chromium/add_entries_to_the_spki_blocklist.patch) distrust of these specific eMudhra certs ([GHSA](https://github.com/electron/electron/security/advisories/GHSA-jr5w-w6x2-84p9)), which requires users to install a full new version of any electron application before the patch lands. This is a one-time bandaid and without revocation list support, the next time something similar happens the patching has to repeat.

## How bad could it be

This year I reported updates without signature verification to [Proton](https://schaerli.org/weblog/5-proton/#unsignedclients), [Bitwarden](https://github.com/bitwarden/clients/pull/19591), [Internxt](https://schaerli.org/weblog/6-internxt/#unverifiedupdates) and [Filen](https://schaerli.org/weblog/7-filen/#cryptodoesntmatter), so I knew they weren't rare. I had my LLM compile a list of notable Electron apps, install them in a lab, and test which still trust the eMudhra certs _(using the new [emudhra option](https://github.com/mitmproxy/mitmproxy/blob/992052ee92d7ff4d240eafbe1afdf87c94b3f080/web/src/js/ducks/_options_gen.ts#L26) in [mitmproxy](https://github.com/mitmproxy/mitmproxy))_. It then read the code to check whether each app allows in-place updates and, if so, whether they require a signature check.

![Scan results by OS. Top left: patched and verifies update signatures (e.g. Signal). Bottom left: still trusts eMudhra but verifies updates (e.g. Bitwarden). Top right: patched but unverified updates (e.g. ProtonMail). Red: unpatched and unverified (e.g. Internxt).](img/quadrants.svg)

Even if there exists a version that no longer trusts eMudhra, many users still run old versions and without update signatures they patch through an insecure channel which allows remote code execution (RCE) for any attacker on the network.

> ¹ Squirrel.exe update traffic does not use the Electron trust store but the OS trust store, so it depends on the OS patch level. Microsoft [disallowed the compromised keys](https://www.microsoft.com/en-us/msrc/blog/2026/10/microsoft-response-to-compromised-emudhra-certificate-authority-keys) in the Windows store in October.
>
> ² Proton's desktop apps and Threema pin the certificates of their main API in the app, meaning the main traffic is limited to a small set of certs and does not trust the eMudhra certs. The pin does not apply to the update traffic.
>
> ³ Delta Chat rejected the chain despite being unpatched, every connection it makes runs through its Rust core and not the Electron stacks the vulnerability lives in.

Proton Mail [patched quickly](https://github.com/ProtonMail/WebClients/blob/proton-inbox-desktop@1.16.1/applications/inbox-desktop/package.json#L82), but on Windows it still updates without a signature check. Proton pins its own certificates for most traffic, but not for updates, which run in a separate [Squirrel.exe](https://github.com/Squirrel/Squirrel.Windows) process that uses the OS trust store. The same goes for any Windows app using Squirrel which relies on the OS trust store, not Electron's, so an up-to-date OS won't trust the eMudhra certs. One thing I missed in my [first review of Proton](https://schaerli.org/weblog/5-proton/) is how the Proton Mail desktop app [fetches](https://github.com/ProtonMail/WebClients/blob/proton-inbox-desktop@1.16.1/applications/inbox-desktop/src/utils/view/viewManagement.ts#L161) its entire UI from [`mail.proton.me`](https://github.com/ProtonMail/WebClients/blob/proton-inbox-desktop@1.16.1/applications/inbox-desktop/src/store/urlStore.ts#L48-L52). This is not ideal for an end-to-end encrypted desktop app, as whoever runs the server has the technical means to serve a backdoored UI to selected users on any launch, even if the app itself is properly signed. The same applies to the [Padloc](https://github.com/padloc/padloc/blob/v4.3.0/packages/electron/src/main.ts#L137-L138) password manager and [Rocket.Chat](https://github.com/RocketChat/Rocket.Chat.Electron/blob/4.19.1/src/ui/components/ServersView/ServerPane.tsx#L158-L164).

If you use an app from this list that still trusts the eMudhra certs, uninstall it for now. If it also updates without signatures, don't patch it through the auto-updater. Download the new version in your browser instead, where the compromised CA is already distrusted.
